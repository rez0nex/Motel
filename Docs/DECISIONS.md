# Технические решения Motel

## 2026-10-31 — первый эпизод Леонида

По текущему запросу прямое близкое предупреждение заменяет расширенную цепочку карточки/слухового аппарата. Один NPC в номере 4, одна переносимая трость без инвентаря, диалог с выбором. UI переиспользуемый: окно принимает текст и действия вариантов, состояние задачи остаётся у Леонида. Диалог блокирует управление и мировой луч, но не время; Escape закрывает окно и включает общую паузу. Авария закрывает диалог до перезагрузки.

Для фиксированной принятой геометрии достаточно заданных точек пути через запасной выход, CharacterController и капсульной проверки реальных препятствий. Новый навигационный пакет не добавляется. NPC не открывает двери, не выбирает обход автоматически и не телепортируется при блокировке: ждёт игрока и продолжает после освобождения. Спасение — фактическое прибытие на ориентир парковки, не начало движения. Альтернативный маршрут и сопровождение по близости остаются за границами текущего эпизода.

Проверка в Play Mode выявила оттеснение NPC открывающимся полотном в угол. Поэтому точки ожидания находятся вне размаха двери, а пересечение начинается после полного открытия. У PrototypeDoor добавлен только читаемый признак завершения открытия; работающая анимация, размеры и взаимодействие двери не меняются.

Текущие сон/предупреждение/перенос/движение/спасение принадлежат сцене и сбрасываются. Постоянное знание `leonidRescued` — необязательное поле прежнего JSON версии 1 рядом с `cutoffCausedExplosion`; старый файл без него читается как «ещё не известно». Флаги независимы, повторное получение не пишет копии. Тесты направляют знания в отдельные файлы Temp; пользовательский файл не использовать как тестовые данные. Взрыв сохраняет прежний общий переход и не открывает финал после одного спасения.

Решения из доступной истории и текущего кода; даты их принятия не установлены, кроме явно указанных. Мелкие правки ведутся в журнале.

## Среда и зависимости

Использовать установленную Unity **6000.6.7f1**, подключённые Input System **1.20.1** и URP **17.6.0**. Не добавлять сторонние зависимости для первого прототипа: необходимых средств уже достаточно в проекте. Материалы генератора используют URP/Lit.

## Управление и ввод прототипа

Ходьба и гравитация выполняются через CharacterController; прыжок и бег не входят в первый этап. Действия Input System задаются отдельной картой в коде: шаблонный Interact использует удержание, а прототипу нужно одиночное нажатие E. Это сохраняет исходный Input Actions asset без изменений.

В исходном Prototype освобождённый курсор отключает ходьбу, обзор и взаимодействие; гравитация и дверь продолжаются. Для MotelBlockout это правило заменено общей паузой ниже: часы и симуляция останавливаются вместе. Шаблонные сцены не меняются.

## Взаимодействие и дверь

Луч идёт из центра камеры до 2,5 м и учитывает первое твёрдое препятствие. Проверка всех препятствий сохраняет блокировку взаимодействия стенами. Игрок находится на встроенном слое Ignore Raycast, чтобы не перекрывать собственный луч.

Дверь использует кинематический Rigidbody на петле и дочернее полотно с BoxCollider. Поворот выполняется через MoveRotation в FixedUpdate: точка вращения находится на краю полотна, а дверь участвует в столкновениях.

## Создание сцены и интерфейс

Тестовую сцену создаёт отдельный Editor-инструмент с фиксированным путём `Assets/Scenes/Prototype.unity`. Вместо добавления объектов в существующую сцену он создаёт новую; перед перезаписью требует подтверждения и повторно использует материалы. Это упрощает воспроизведение прототипа и сохраняет SampleScene. Поведение генератора ещё требует проверки в Unity.

Прицел и подсказки используют встроенный IMGUI, чтобы не требовать дополнительных UI-ресурсов для этого этапа.

## 2026-10-30 — ведение документации

Журнал хранит выполненную работу и результаты проверок, TASKS — текущие статусы, DECISIONS — существенные решения с причинами, README — инструкции запуска и проверки. Обязанности по чтению и обновлению закреплены в корневом AGENTS.md. Такое разделение позволяет не копировать одинаковые инструкции в несколько документов.

## 2026-10-30 — ветки разработки и сохранение этапов

Разработка ведётся в постоянной `dev`, а `main` хранит завершённые и проверенные этапы. Пользователь разрешил обычные commit, push и merge в рамках постоянного цикла без подтверждения каждой команды. После проверки изменений, обновления Docs и необходимой ручной приёмки этап сохраняется в dev, отправляется в origin/dev и сливается в актуальную main с merge-коммитом. После push main работа возвращается в dev, которая включает main и также отправляется в origin. Dev после слияния сохраняется. Полный порядок и действия при ошибках — в [AGENTS.md](../AGENTS.md).

Перед работой выполнять fetch и при необходимости включать origin/main в dev обычным слиянием; уже существующие слияния учитывать по истории. Не использовать squash, rebase, force push или переписывание опубликованной истории. Это сохраняет историю этапов и позволяет завершать каждый цикл в синхронизированных ветках с чистым рабочим деревом.

## 2026-10-30 — сериализация настроек URP

Сохранить `m_ProjectSettingFolderPath: URPDefaultResources` в ProjectSettings/URPProjectSettings.asset. В исходнике установленного URP 17.6.0, Editor/DefaultScene/UniversalProjectSettings.cs, это сериализуемое поле имеет то же значение по умолчанию. Правка фиксирует настройку редактора, не меняя игровую логику; откат не требуется.

## 2026-10-30 — GDD и первый блокинг планировки В (до увеличения номеров)

GDD хранит целевой дизайн. Перед изменением механики читать относящиеся к ней разделы; новые согласованные решения отражать в GDD и этом файле. Текущий блокинг ограничен геометрией и прежними механиками прототипа: описание будущих систем не расширяет объём задачи.

Для MotelBlockout выбран вариант В по скрину: северный ряд 1–4, южный 5–8 справа от общего служебного прохода, ресепшен внизу, парковка внутри угла. Северные комнаты шире южных, чтобы сохранить композицию, служебный проход и обычные южные номера около 4 × 5 м. Кабинет и техническая не включены в маршрут выхода. Соединительная дверь 7–8 расположена ближе к коридору для обхода мебели; основная дверь 8 остаётся «Подсобкой».

Геометрия задаётся одной моделью MotelBlockoutPlan, используемой и Editor-генератором, и отдельной программной проверкой. Это связывает проверяемые размеры с создаваемыми объектами. Игрок и двери копируются из сохранённой Prototype с сохранением ссылок и настроек; механики не переписываются. У закрытых номеров нет компонента взаимодействия. Потолки выделены в отдельную группу; материалы блокинга хранятся отдельно от материалов Prototype. Размеры и ручная проверка — в [MOTEL_BLOCKOUT.md](MOTEL_BLOCKOUT.md).

## 2026-10-30 — физические таблички вместо GUI-материала в мире

Для табличек используется TextMesh с размером, ограниченным по фактическим границам глифов, а не по одному fontSize. Цифры стоят на плашках 0,28 × 0,22 м, длинные названия — до 0,86 × 0,22 м; буквы не выше 0,15 м и не шире 0,8 м. Нейтральная подложка улучшает читаемость у двери. Большие пояснения ресепшена и места сбора удалены из игрового пространства; зелёный ориентир сбора сохранён.

Материал текста использует отдельный URP-шейдер WorldSignText: ZTest LEqual, ZWrite On, Cull Back и alpha clip. Причина: встроенный GUI/Text Shader в сравнительном рендере отображал текст за стеной и с обратной стороны. WorldSign привязывает текущий атлас динамического встроенного шрифта через MaterialPropertyBlock при включении и перестройке атласа; общий материал не меняется. Это сохраняет корректность после загрузки сцены и в игре без новых зависимостей. Таблички не имеют коллайдеров и не участвуют в UI или взаимодействии; прежний PrototypeInteractor остаётся единственным источником экранной подсказки.

## 2026-10-30 — увеличенный переиспользуемый модуль номера

Последнее изображение и ориентир 5 × 6,5 м внутри заменяют прежние размеры номера. Оба ряда используют один MotelGuestRoomModule с отражением только глубины Z. Это сохраняет вход/прихожую слева, один санузел справа и горизонтальную кровать изголовьем вправо. Внутри: прихожая 2 × 2,3 м, санузел 2,84 × 2,3 м, жилая часть 5 × 4,04 м; две перегородки толщиной 0,16 м. В спальню ведёт открытый проём слева; в санузел только отдельная дверь из прихожей.

Ряды выровнены, гостевое крыло расширено вправо и в глубину; двор, парковка и наружный обход подстроены к новым границам. Положение служб сохранено. Кровать 2 × 1,6 м и исходный CharacterController не уменьшаются; ширина проходов проверяется по реальным коллайдерам и открытым полотнам, дополнительно — окружностью диаметром 1 м. Восьмой шкаф поставлен справа, соединение 7–8 сдвинуто за санузлы в жилую часть. Пользователь принял размеры и положение стойки после ручной проверки в Unity.

Существующий PrototypeDoor используется с шириной полотна под конкретный проём и противоположным знаком угла для отражённого ряда. Изменяется конфигурация экземпляра, не механизм взаимодействия. Высота, толщина, скорость двери и дальность E сохраняются. Таблички используют прежний исправленный рендер; идентификаторы включают номер двери, поэтому одинаковые тексты «Санузел» не создают одинаковые объекты.

Стойка ориентирована лицевой стороной к восточному входу; игрок стоит западнее и смотрит на вход (Y = 90°). Для повторного создания генератор открывает сохранённый Prototype как неизменяемый шаблон перед созданием новой сцены: Unity не допускает требуемую аддитивную операцию рядом с несохранённой пустой сценой. Перед этим остаются подтверждение перезаписи и запрос сохранения текущих изменений.

## 2026-10-30 — приёмка черновой геометрии без полировки

Текущая планировка, размеры номеров и расстановка стойки приняты пользователем после ручной проверки. Мебель и сантехника остаются временными примитивами для последующей замены моделями. Текстуры и окончательное освещение выполняются позже, отдельными задачами; дополнительная полировка сейчас не требуется. При замене оформления сохранять принятый масштаб и свободные маршруты. Это отделяет проверку локации от будущего художественного оформления.

## 2026-10-30 — шестиминутная петля и надёжный сброс

По новому согласованию попытка длится 360 секунд активного времени от 20:16 до 20:22; прежние 600 секунд и 20:26 заменены в GDD и расписании. События персонажей сжаты в расписании, но остаются планом. Для проверки F6 на паузе явно включает ×6: тот же цикл за 60 настоящих активных секунд. Сохранённая сцена и новый запуск сборки используют обычную скорость; отладочная скорость сохраняется только внутри игровой сессии между сбросами.

AttemptClock — небольшой независимый источник игрового времени и защита одного запроса аварии. MotelLoopController сцены отвечает за паузу, эффекты и загрузку той же сохранённой сцены. Перезагрузка восстанавливает исходные двери, игрока, свет и оборудование без ручного списка сбрасываемых компонентов. Таймер и аварийная кнопка сходятся в один обработчик; после первого запроса взаимодействие заблокировано. Постановочное повреждение и обломки заранее созданы неактивными, не размножаются при аварии. Звук и физическая разрушаемость в этот этап не входят.

В MotelBlockout Escape, потеря фокуса и J ставят Time.timeScale = 0; часы также явно проверяют паузу. Закрытие J продолжает, Escape оставляет свободный курсор и паузу. Владение курсором передаётся от FirstPersonController контроллеру петли только в этой сцене: Prototype сохраняет прежнее поведение. Двери и аварийная кнопка используют один прежний луч с первым препятствием и дальностью 2,5 м, один прицел и одну экранную подсказку.

ObservationStore находится отдельно от загружаемой сцены; единственный факт хранится флагом, без дубликатов. JSON версии 1 сохраняется в persistentDataPath через временный файл и атомарную замену/перемещение. Повреждённый или будущий формат не перезаписывается; ошибка чтения/записи видна в окне наблюдений, знания текущей сессии продолжают работать. Полный журнал и остальные данные GDD пока не сериализуются.

## 2026-10-30 — окна и демонстрационная сборка

Наружные стены разбиваются на простенки, подоконную часть и перемычку под девять проёмов 1,6 × 1,1 м. Подоконник 1,1 м; стекло с твёрдым коллайдером не является выходом. Окна номеров находятся левее кроватей и правее столов, вдали от шкафов/изголовий; мебель и размеры комнат сохранены. Стекло использует прозрачный URP/Lit без новых ассетов и зависимостей.

Сборка Windows x64 выполняется существующим редактором и явным списком из одной MotelBlockout, без изменения пользовательского Build Profile и без второго Unity. Результат находится в исключённой Builds; подготовка сборки и проверка её запуска отмечаются отдельно от компиляции и ручной приёмки.

После фактической ошибки виртуальной памяти проверки компиляции и сборка выполняются последовательно. На время сборки `BEE_BUILD_THREADS=2`, `DOTNET_PROCESSOR_COUNT=2` и число job workers ограничиваются двумя, затем прежние значения восстанавливаются. Внешняя проверка также ограничивает .NET и использует Editor response-файлы, исключая незавершённые Player-артефакты. Это не меняет игровые настройки и не требует правки системного файла подкачки.

## 2026-10-30 — сохранение итога дня до полного ручного маршрута

По прямому запросу пользователя текущая реализация сохраняется обычным циклом dev → main → dev на основании фактически выполненных автоматических проверок и проверки запуска сборки. Полная ручная приёмка не заявляется и остаётся открытой задачей. Это разрешение относится к сегодняшнему сохранению и не меняет постоянные инструкции AGENTS.md. Сериализацию настроек URP/графики и preloaded Input Actions включить вместе с рабочей сборкой этапа; отдельное переключение UnityConnect, не связанное с игровыми функциями, сохранить локально вне коммита.
